# FlowSQL 产品定位与近期投入方向分析报告

日期：2026-09-29  
归档状态：讨论结论与阶段性建议；产品定位尚未确定  
代码与文档核查基线：`b6e934b`  
分析对象：托管式离线数据分析平台、本地实时数据采集分析系统

## 1. 结论摘要

在尚未取得明确的付费客户和部署需求证据、研发投入需要集中的前提下，建议采用：

> **离线分析产品优先，本地可交付，托管待验证。**

近期先选择一种用户和一个重复发生的分析任务，补齐该场景所需的分析与结果使用体验，通过真实数据验证价值。
随后根据数据能否外传、使用频率、部署要求和付费意愿，决定重点投入租户平台还是生产实时采集。

这项建议不等于已经选定云端多租户模式，也不要求永久放弃实时方向。若已有客户明确需要持续监测，
愿意提供网络环境并约定验收条件或试点费用，则应优先评估范围明确的本地实时系统。

报告中的商业比较属于条件化推断，不是市场调查结论。当前未确认团队规模、预算、客户数量、渠道、
可上传数据的比例和付费意愿；不能将“尚未取得这些信息”视为“实际没有客户”。

## 2. 决策背景与边界

本次讨论源于两种候选路线及其研发顺序：

- **路线 A：托管式离线分析平台。** 用户上传 PCAP 或日志，租用分析空间、算力和存储；拟先补齐离线分析，再建设租户与平台能力。
- **路线 B：本地实时采集分析系统。** 在客户环境持续采集和分析流量；拟先实现实时采集，再补齐分析能力。

两者都能服务企业用户。“是否属于 B 端”不能帮助区分这两种路线，应重点比较用户价值、数据流转、成本和交付责任。
研发顺序也不必由部署形态机械决定：实时系统需要有用的分析结果，离线平台需要真实的托管需求，
任一路线都应先验证一个具体任务，而不是等待整套基础设施和全部分析模块完成。

托管/本地与离线/实时是两个独立维度：

| 部署方式 | 离线分析 | 持续分析 |
| --- | --- | --- |
| 服务商托管 | 上传有限数据集，按任务使用分析空间 | 外部系统持续提交数据，由平台持续处理 |
| 客户本地部署 | 在客户环境内上传、分析和保存 PCAP 或日志 | 在客户网络内持续采集、分析与监测 |

**本地部署的离线分析产品是可行的验证起点。** 它让数据留在客户环境内，也能检验分析能力是否值得持续使用；
以后选择托管或实时路线时，分析核心仍可复用。这是验证路径，不建议现阶段同时建设四种完整产品。

## 4. 两条路线的综合比较

| 维度 | 托管式离线分析平台 | 本地实时采集分析系统 |
| --- | --- | --- |
| 核心购买理由 | 减少环境搭建，批量处理数据，复用分析方法和共享结果 | 及时发现问题，留住偶发故障证据，持续观察网络状态 |
| 使用频率 | 测试回归和技术支持可能高频；单次故障排查可能低频 | 系统持续运行，但仍须证明输出对用户有用 |
| 数据接入门槛 | 能否外传、上传耗时、是否已有可用输入文件 | 镜像流量获取、采集位置、部署权限和环境适配 |
| 收入模式 | 按任务、用量或团队订阅；计费方式取决于工作频率 | 项目交付、节点或年度授权、维护服务；需验证购买流程 |
| 获客与销售 | 有机会自助试用；企业仍会评估数据管理和采购要求 | 可能依赖行业关系、集成渠道、现场试点与验收 |
| 成本承担 | 服务商承担计算、存储、运行维护和用户支持 | 客户承担主要硬件资源；厂商承担适配、升级和交付支持 |
| 主要技术投入 | 数据与执行隔离、资源配额、调度、生命周期和用量记录 | 长期采集、丢包可见性、背压、时间推进、恢复和容量管理 |
| 现有替代方式 | Wireshark/tshark、脚本、Notebook、既有分析服务 | 既有监测工具、采集设备和可观测性系统 |
| 差异化机会 | 将专家分析方法转成团队可重复、可比较的任务 | 将持续采集证据与可解释的分析结果连接起来 |
| 主要失败风险 | 用户愿意分析却不能上传，或使用过于偶发、收入难覆盖成本 | 能采到包但不能改善排障，适配与现场支持吞噬研发投入 |
| 更有利的前提 | 有可上传数据、重复任务和托管使用意愿 | 有明确监测需求、真实部署环境和共同验收的客户 |

以上是结构性比较，没有足够依据给出市场规模、收入预测、开发工期或带精确分值的路线排名。

## 5. 影响结论的关键因素

### 5.1 数据能否进入托管平台

PCAP 可能包含内部网络结构和业务通信信息。用户需要分析，不代表其组织允许原始数据离开内部环境。
不同日志类型也应分别确认可外传范围，不能假定“日志都可以上传”。

上传耗时也是使用成本。以十进制单位估算，20 GB 文件通过持续可用的 100 Mbit/s 上行传输，
理论耗时约为 `20 × 8 × 1000 / 100 = 1600 秒`，即 27 分钟；实际还受链路利用率和协议开销影响。
如果本地方法已经足够快，单靠更强云端算力未必能够补偿传输成本。

因此，托管路线首先要验证数据可达性与用户收益。用户不能上传，但分析需求成立时，应评估本地离线交付，
不能直接推导为必须开发实时采集。

### 5.2 使用频率与收入匹配

偶发故障分析更适合先测试按任务或短期用量收费；长期租用空间需要稳定的重复任务支撑。
设备回归、版本性能对比、网络变更验收和批量技术支持是值得验证的候选场景，并非已经确认的客户需求。

“租用算力和存储”是资源交付与计费方式。对外价值应落在用户完成分析的时间、可重复性、结果质量与团队使用成本上。
若只售卖通用资源规格，容易与通用云计算服务直接比较。

可以在试点中记录单次任务成本构成：计算占用、输入及结果存储、数据传输和支持投入。
本地交付则应记录授权收入之外的售前、安装、适配、验收和维护成本。不能仅比较云端账单与客户硬件费用。

### 5.3 多租户与自定义算子的责任

当前 C++ 算子通过 `dlopen` 加载，Python 算子也在 Worker 中执行。面对跨客户共享服务，
账号和数据表中的租户归属字段不足以约束用户代码、进程崩溃、文件访问和资源消耗。

托管第一版可以评估受控算子目录与隔离执行环境，明确任务资源上限，再逐步开放扩展能力。
采用独立部署单元也需要配置、数据与权限管理，不能简单把每人一个容器等同于隔离方案已经完成。
具体执行隔离方案应在决定开展托管试点后设计，本报告不提前选定实现方式。

### 5.4 实时系统需要持续运行的业务价值

实时采集特别适合“故障偶发、事后无法重新取得流量”的场景。若客户确实需要留存现场证据，
离线上传不能独立解决问题，此时实时接入有直接价值。

相应的交付还包括采集质量说明、断流与过载处理、故障恢复、状态与存储上限。客户需要知道结果是否完整，
以及系统异常时还有哪些证据可用。接通网卡本身不足以完成这类交付。

原始数据的规模同样影响设计。持续 1 Gbit/s 按十进制字节折算约为每天 10.8 TB，
这是未计额外开销、未考虑过滤和压缩的示例，不是 FlowSQL 的实测吞吐或必需存储量。
是否保留全包、保留多久、输出哪些摘要，应由目标任务决定。

### 5.5 客户渠道可能改变技术优先级

能够提供真实数据、部署环境、明确验收人和试点预算的客户，比泛泛的产品兴趣更能指导方向。
若现有行业关系能促成一个范围明确的实时试点，即使技术建设量更大，也可能比从零获取托管用户更接近收入。

反过来，若有稳定上传数据并反复分析的用户，却缺乏进入客户网络的条件，则托管离线平台更值得投入。
本报告未获得这些信息，推荐顺序须随证据更新。

### 5.6 分析投入的复用价值

分析准确性、指标语义、结果表达、参数化任务和比较能力，未来托管与本地、离线与实时都能使用。
它们的适用范围比完整计费平台或多个网卡采集后端更广。

因此，现阶段更适合围绕一个真实问题补齐分析链路，而不是先完成全部协议清单。
日志扩展也应服务同一个问题，例如补充网络故障相关的访问日志；通用文本读取不等于通用日志分析能力。

## 6. 阶段性投入建议

| 工作 | 建议顺序 | 开始或扩大投入的依据 |
| --- | --- | --- |
| 确认一种用户和一个重复任务 | 优先 | 能取得真实样本并了解现有处理方式 |
| 补齐该任务所需的分析和结果体验 | 优先 | 能明确比较原方法与 FlowSQL 的效果 |
| 使用 Docker 开展受控本地试用 | 优先用于验证 | 数据必须留在本地，或需要先降低试用门槛 |
| 托管工作空间与租户能力 | 条件满足后 | 数据可以交付、用户反复使用、有付费及资源隔离要求 |
| 生产实时采集与接入 | 条件满足后 | 缺少连续数据已成为主要障碍，且有环境和验收标准 |
| 多种高速采集后端 | 后续按需 | 已选场景暴露出明确的性能或适配限制 |
| 通用日志平台扩张 | 后续按需 | 已识别具体日志类型、分析问题及重复使用需求 |

建议的候选价值表述为：“帮助网络运维、测试或技术支持团队，把一次性的专家分析沉淀为可重复执行、
结果可回查的分析流程。”这是待用户场景验证的表述，不作为当前已经批准的品牌定位。

如果选择实时试点，先限定一种采集方式、一个受支持环境、一组有用指标与容量边界。
可利用已有采集工具验证端到端价值，出现明确限制后再决定自建部分；无需先覆盖全部后端。

## 7. 验证计划与路线选择条件

建议安排一个约 2～4 周的产品验证窗口。这是收集决策证据的建议周期，不是开发完平台或实时系统的承诺，
也不表示本次归档已经启动试点。

| 步骤 | 要取得的材料 | 要回答的问题 |
| --- | --- | --- |
| 选择用户与任务 | 一类用户、一项具体任务及现有工作过程 | 问题是否经常出现，谁使用、谁评价、谁付费？ |
| 取得真实数据 | PCAP 或明确类型的日志、规模与可用范围 | 能否进入托管平台，是否必须留在本地？ |
| 完成一次分析 | 原方法与 FlowSQL 的结果、耗时和人工步骤 | 结果是否可信，是否减少用户工作？ |
| 验证再次使用 | 下一批数据、使用频率、重复执行要求 | 是否值得订阅，或更适合按次交付？ |
| 形成有约束试点 | 时间、责任人、验收条件、预算或试用承诺 | 用户是否愿意为结果继续投入？ |

按以下信号调整路线：

| 获得的证据 | 更合适的下一步 |
| --- | --- |
| 数据可上传、需求重复、有托管意愿和可解释成本 | 开展托管离线工作空间试点，补足隔离与资源管理 |
| 数据不能外传，但离线分析价值已验证 | 交付本地离线产品，继续验证分析能力与维护成本 |
| 主要困难是拿不到故障期间的数据，且有持续采集环境与验收需求 | 优先开发有限范围的本地实时分析系统 |
| 只能得到兴趣表达，没有真实数据、再次使用或试点承诺 | 继续缩小用户任务，暂缓完整租户平台和多后端采集投入 |
| 现有分析结果无法帮助用户完成任务 | 优先改善分析价值，不能靠增加租户或采集方式解决 |

没有客户证据时，不建议用既有代码量、技术兴趣或基础设施完整性代替路线选择。

团队投入与运维能力、现有销售渠道、可提供的试点环境及付费意愿。
