# Feature: 产品版本与构建信息

标识：`product-version`；优先级：P1；状态：`[x]` 已完成（按用户确认的 Feature 聚焦验收边界）。
前置：现有标准 CMake 产品构建、Web 静态资源、Python Worker 启动器和 Docker 预编译产物打包路径。

## Non-Goals

- 不实现自动推断版本增量、自动打标签、提交、推送、镜像上传或 CI/CD 平台接入。
- 不实现集群服务版本汇总、自动升级、兼容性协商、回滚或更新通知。
- 不改插件 ABI、业务结果 Schema、配置资源 revision、第三方依赖版本或产品定位。
- 不承诺凭版本信息即可证明二进制逐字可复现、供应链签名或全部服务已升级；构建信息不包含主机、用户和秘密。

## 业务意图与范围

让开发、部署与故障排查人员通过 Web、命令行或交付文件，识别当前产物的产品版本、源码提交与本地修改状态，
并在交付前核对源码和各项产物属于同一构建，避免仅更改镜像标签或前端文字就把旧产物当作新版本。

当前 Web 从前端 package.json 读取 0.0.0，Worker 分发元数据独立写死 0.1.0，C++ 主程序没有 --version，
Docker 使用预编译产物且 Compose 引用 latest；本 Feature 建立统一来源与可核查的交付路径。
范围包括版本源、构建快照、C++/Worker CLI、Web 展示及 HTTP 查询、原生/Docker 打包校验和发布说明。

## 版本来源与升级约定

- 仓库根目录 VERSION 是产品版本唯一人工维护来源，UTF-8 单行、不带 v 前缀；缺失或格式非法直接失败。
- 首次实施使用 0.1.0 作为版本基线；登记规格不会创建 VERSION、发布该版本或表示此前验收已补齐。
- 首版接受 SemVer 的固定子集：MAJOR.MINOR.PATCH，可附 -dev.N、-alpha.N、-beta.N 或 -rc.N；
  各数字为无前导零的非负整数；不接受 + 元数据。源码身份单独存储，避免两套构建信息来源。
- 示例：0.1.0-rc.1 为候选、0.1.0 为交付基线、0.1.1 为兼容修复、0.2.0 为新增能力或 0.x 阶段的适配性调整；
  1.0.0 起确立稳定兼容承诺，不兼容调整升主版本。开发提交用 revision 区分，不自动递增产品版本。
- Web 显示与 Git 标签添加 v 前缀；镜像标签和产物文件名使用无前缀版本。是否可发布由显式校验决定。
- 前端包版本不再作为产品展示来源，产品构建不改写已跟踪的 package.json 或 lockfile。
- Worker 分发版本从同一来源派生为 PEP 440：正式版保持原值，dev/alpha/beta/rc 分别映射为 .devN/aN/bN/rcN；
  例如 0.1.0-rc.1 对应 0.1.0rc1。运行时仍报告原始产品版本，源码与分发包均携带所需版本文件。
- CMake project VERSION 仅使用三段数字，完整产品版本保留预发布后缀；版本生成不依赖特定主机 Python 安装路径。

## 构建信息数据契约

同一产品构建的所有消费者取得同一只读快照，JSON 固定包含以下三个字段，不写入构建时间：

```json
{
  "version": "0.1.0",
  "revision": "e55c1ec55bc866e6fa59f16223a5cfe003feb08b",
  "dirty": false
}
```

| 字段 | 类型与语义 |
| --- | --- |
| version | string；VERSION 中的完整产品版本，不带 v，不由 Git 标签或运行时环境变量覆盖。 |
| revision | string 或 null；构建源码的完整 Git commit ID；无 Git 元数据时为 null，不伪造提交。 |
| dirty | boolean 或 null；源码相对该提交是否有修改；无 Git 元数据或不能确认时为 null，不伪报干净。 |

dirty 包括已暂存、未暂存的跟踪文件变化及未忽略的新文件；忽略的 build、evidence 与依赖缓存不计入。
Git 信息不可得时允许普通源码包构建；VERSION 仍必需，revision/dirty 未知，正式发布校验拒绝未知身份。

实现前冻结公共值类型和只读访问声明，字段与 JSON 一一对应；各目标内置自身构建快照，不新增插件接口或 IID：

```cpp
#include <optional>
#include <string>
namespace flowsql {
struct ProductBuildInfo {
    std::string version;
    std::optional<std::string> revision;
    std::optional<bool> dirty;
};
const ProductBuildInfo& GetProductBuildInfo() noexcept;
}
```

- 标准入口仍为 cmake -B build src 与 cmake --build build；普通构建生成快照并驱动全部消费者，
  不把产品版本写入共享第三方缓存，不要求调用方手工传入额外版本参数。
- VERSION、提交或源码 dirty 状态变化后，普通增量构建更新快照及关联消费者；无变化不重写生成文件，
  不重复 npm ci，也不因版本变化重新构建第三方库。构建期间不支持并发编辑或切换源码提交。
- C++ 头、Worker 版本模块、前端常量与 build/output/build-info.json 从同一快照派生；构建只写生成区域。
- 产物运行后只报告其内置信息，不读取当前 Git 或源码 VERSION 来重标已有二进制；移动原生产物后仍可查询。
- 前端独立 npm run dev/build 也从仓库 VERSION 及同规则读取源码身份，不要求先运行 CMake；开发服务需响应版本源变化。

## 查询与展示契约

- flowsql --version 与 flowsql-worker --version（含 python -m flowsql.worker --version）成功退出 0，
  输出三行：FlowSQL <version>、revision=<完整提交或 unknown>、dirty=<true/false/unknown>。
  该路径不加载插件、不读部署配置、不发现算子、不连接外部服务或监听端口。
- GET /api/version 返回 HTTP 200、application/json，响应体为上述三个字段，Cache-Control: no-store；
  同时支持 Web 直接监听入口和现有路由枚举入口，不改 /api/health 的现有响应。
- HTTP 返回当前 Web 插件自身构建信息，不能被主程序版本或磁盘上后来替换的文件覆盖，也不代表远端 Scheduler/Worker。
- Web 顶栏与保留的侧栏版本位使用前端构建常量，显示 v<version>；悬浮详情显示短提交与修改状态，未知值明确显示未知。
  前端不等待后端请求才显示版本，也不以 API 结果覆盖自身构建身份；后端详情可由版本接口单独核查。
- 后端序列化与 CLI 共享值契约；普通构建的未知身份须如实呈现，不回退到 v0.0.0。

## 交付与发布契约

- 原生交付携带 build-info.json 和内置同一信息的 C++、Worker、静态资源；发布校验读取实际产物，
  比较三字段，不能只看源树 VERSION 或重新生成一份清单覆盖旧产物。
- Dockerfile 仍打包预编译产物；镜像中的 Worker 运行时版本取自所交付快照，不能用打包时新源码重标旧产物。
  打包入口校验实际输入版本身份一致；镜像 version/revision OCI 标签从通过校验的产物生成，拒绝参数与产物不符。
- Compose 支持通过同一 FLOWSQL_IMAGE 选择所有产品服务镜像，默认 flowsql:latest；部署具体版本时可指定
  flowsql:0.1.0。部署变量只选择镜像，不修改镜像内版本，latest 不作为发布身份依据。
- 正式/候选发布校验要求源码干净、身份已知、VERSION 与请求版本及精确 Git 标签 v<VERSION> 一致，
  标签解析到当前提交，且所有待交付产物字段与该源码一致；任一不符非零退出，不自动改版本、打标签或修复产物。
- 常规开发构建允许无标签或 dirty=true；发布工具只校验，创建标签、推送和上传仍由用户明确授权。
  基础发布顺序为版本变更提交 → 构建/验收 → 显式建立对应标签 → 发布校验 → 授权后交付。
- 用户说明记录版本升级规则、查询方式、镜像选择和上述发布步骤；版本登记与发布校验不替代产品功能验收。

## 主链路

1. 开发者维护 VERSION → 构建生成源码身份快照 → 派生 C++/Worker/前端与清单 → 运行 CLI、HTTP 或 Web
   查询各自产物身份；普通增量构建保持变化可见，无 Git 的源码包仍给出真实的未知身份。
2. 交付者从指定提交构建验收并建立标签 → 发布校验核对源码、实际输入产物和标签 → 打包携带相同元数据的
   原生包/镜像 → 部署者选择具体镜像并查询运行版本；不一致时停止交付，保留非秘密错误证据。

| 版本解析与派生 | 正式/四类预发布、非法前缀/前导零、缺失源、CMake 数字版本及 PEP 440 映射；JSON null 与 false 区分。 |

- 解析、Git 夹具、生成与发布失败路径使用隔离临时目录；新增测试登记统一依赖清单，纯单测不启动数据库或 Kafka。

- 每个 Task 在工作台冻结所选测试、位置、权限及命令；标准完整构建已通过，按用户明确要求聚焦版本 Feature，
  验收清单为五个版本相关套件、实际产物身份、镜像版本传递及参数拒绝；所选清单须全部执行通过，零跳过/未执行。

  镜像夹具仅复用固定 ID 的运行依赖、完整保留生产打包指令，须记录派生依据及实际使用产物摘要；不得以配置解析代替运行。
